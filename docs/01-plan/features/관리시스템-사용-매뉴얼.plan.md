## Executive Summary

| Perspective | Content |
|-------------|---------|
| **Problem** | 관리시스템은 메뉴 9개, 예산관리 하위 탭 9개, 관리자 탭 5개로 커졌다. 입금확인증 PDF 일괄등록(F-14), 거래처 자동배정(F-15), HWPX 서식 채우기(F-13) 같은 자동화도 늘었다. 그런데 사용법은 개발자용 `CLAUDE.md`와 설계서에만 있다. 반기 정산·결과보고처럼 몇 달에 한 번 쓰는 기능은 쓸 때마다 다시 알아내야 한다. 앱 안 회계가이드는 규정만 다루고 "어느 화면에서 어떻게 하는지"는 알려 주지 않는다 |
| **Solution** | 기존 `/kihoek` 매뉴얼의 13장+부록 2 골격과 문체를 그대로 따라 `docs/manual/관리시스템.md`를 쓴다. 화면별 사용법, 업무 순서대로 따라 하는 빠른 시작, 업무 달력, 문제 해결을 담는다. 앱 헤더의 「❓ 도움말」은 같은 md 파일을 불러 드로어에 렌더하므로 원천은 하나다. `scripts/check_manual.py`는 매뉴얼에 적힌 화면·버튼 이름을 실제 UI와 대조한다 |
| **Function/UX Effect** | 어느 화면에서든 도움말 한 번이면 그 화면의 절이 열린다(화면 맥락 21개). 화면을 보면서 순서를 따라 할 수 있다. "입금확인증 PDF → 일괄등록 → 증빙 → 상태 → 정산보고서" 한 바퀴와 반기·연말에 할 일을 순서대로 안내하고, 막히면 증상→원인→해결 표에서 찾는다 |
| **Core Value** | 직원 없이 일하는 대표가 개발자나 Claude에게 묻지 않고 시스템을 끝까지 쓰고, 재단 정산·보고 마감을 놓치지 않는다. 화면이 바뀌면 검사가 실패하므로 매뉴얼이 모르는 사이에 낡지 않는다 |

### 1.2 없는 것 (이 기능이 채울 것)

- **웹앱 사용 매뉴얼**: 메뉴 9개(대시보드·예산관리·일정관리·갤러리·게시판·회계가이드·뉴스레터·학교관리·관리자), 예산관리 하위 탭 9개(대시보드·예산편성표·집행등록·일괄등록·거래처 규칙·원천징수계산·집행내역·비용비율·캘린더), 관리자 탭 5개(사용자 관리·수급자 관리·기관 정보·프로젝트 관리·활동 로그) 어디에도 사용 안내가 없다
- **업무 흐름 안내**: 기능은 화면별로 나뉘어 있지만 실제 업무는 여러 화면을 거친다. 예를 들어 입금확인증 PDF는 일괄등록 → 자동배정 확인 → 증빙 자동 첨부 → 집행내역 상태 변경 → 정산보고서 순서로 다룬다
- **앱 안 진입점**: 지금 보고 있는 화면에서 바로 설명을 열 방법이 없다
- **매뉴얼 신선도 장치**: 화면 라벨이 바뀌어도 매뉴얼이 틀렸다는 것을 알릴 장치가 없다

### 2.2 비기능 요구사항

| 정확성 | 코드가 원천이다. 절마다 근거 렌더 함수와 탭 id를 확인하고 쓰며, 설계서와 코드가 다르면 코드를 따른다 |
| 문체 | 견본과 같이 "~합니다/~하세요", 짧은 문장, 표 우선. 화면 요소는 「」로 쓰고 헤딩에는 이모지를 넣지 않는다(앵커 안정) |
| 개인정보 | 예시는 가상값(예: ㈜가나다인쇄)만 쓰고 실제 수취인·학교 실명·계좌·연락처는 금지. 정적 배포로 공개되는 파일이므로 계정·비밀번호·초기 관리자·키도 금지 |
| 성능 | 도움말 관련 요청은 처음 열 때만 발생한다(첫 화면 로딩 변화 0). md는 한 번 불러 메모리에 둔다 |
| 보안 | 렌더 결과는 DOMPurify를 거친다. 외부 링크에는 `rel="noopener"`. CSP는 바꾸지 않는 것이 목표다(jsdelivr·`'self'`가 이미 허용됨) |
| 호환성 | Babel standalone 제약을 지킨다: 훅은 최상위에만, 유니코드 속성 정규식은 `RegExp` 생성자로. 앵커는 GitHub slug 규칙으로 만들어 GitHub 미리보기와 앱에서 같게 한다 |
| 오프라인 | 서비스워커의 network-first 캐시 덕분에 한 번 연 매뉴얼은 앱을 연 채 인터넷이 끊겨도 열린다. 끊긴 상태로 처음부터 다시 읽으면 앱 자체가 뜨지 않는다(서비스워커가 supabase-js를 캐시하지 않는 기존 한계) |
| 분량 | 매뉴얼 900~1,300줄 예상(견본 567줄), `index.html` 증가 250줄 이내 |

### 2.3 범위 제외 (YAGNI)

- **스크린샷·동영상**: 운영 DB 화면에는 실제 수취인·학교가 찍히고, UI가 바뀔 때마다 다시 찍어야 한다. 견본도 글과 표만 쓴다. 후속으로 데모 프로젝트를 만들어 촬영할 수 있다
- **재단 담당자용 장, 인수인계용 구축 문서**(Supabase·Vercel·마이그레이션): 독자는 대표 1인이다. 열람 계정 만들기만 관리자 절의 한 항목으로 넣는다
- **HWPX/PDF 인쇄본**: 이번에 고르지 않았다. 필요하면 `md2hwpx.py`나 `/make-pdf`로 후속 작업한다
- `/promo` 매뉴얼, 개발자 문서: 각각 `SKILL.md`와 `CLAUDE.md`가 맡는다
- 앱 내 전문 검색, 온보딩 투어(말풍선), 다국어
- **앱 동작 수정**(1.4 마감 알림 등): 불일치 대장에 기록하고 별도 fix로 처리한다. 원하면 같은 PR에 묶을 수 있으며 Design에서 확정한다

## 3. 설계 결정

| # | 결정 | 근거 |
|---|------|------|
| D-1 | **단일 원천**: 본문은 md 한 파일이고 앱은 그 파일을 불러 렌더한다(JSX로 옮겨 쓰지 않음) | 사본이 둘이면 언젠가 어긋난다. GitHub, 에디터, 앱에서 같은 글을 본다 |
| D-2 | **견본 골격 1:1**: 13장 + 부록 2, 장 번호와 장의 역할을 유지한다 | 두 매뉴얼을 오갈 때 같은 번호에 같은 종류의 정보가 있다(예: 12장 = 문제 해결). 대표가 이미 읽어 본 형식이다 |
| D-3 | **두 축 구성**: 4장은 화면 순서(찾아보기), 3장·11장은 업무 순서(따라 하기) | 실제 업무는 여러 화면을 거친다. 화면 순서만으로는 "반기 정산 때 무엇을 하지?"에 답할 수 없다 |
| D-4 | **진입은 헤더 버튼(모듈 밖), 표시는 우측 드로어** | `activeProject.modules`로 메뉴가 숨겨져도 도움말은 항상 있어야 한다. 드로어를 쓰면 화면을 보면서 순서를 따라 읽을 수 있다 |
| D-5 | **규정은 링크, 매뉴얼은 "어떻게"만** | 원천징수·적격증빙 규정은 회계가이드가 이미 담당한다. 매뉴얼은 "어느 화면에서 어떻게"를 쓰고 회계가이드 탭으로 안내한다 |
| D-6 | **코드가 원천이고, 차이는 불일치 대장에** | 설계서 중에는 구현하면서 바뀐 부분이 있다. 수행가이드와 앱이 다르면(1.4) 앱 동작을 그대로 옮겨 적지 않고 기록한다 |
| D-7 | **UI 라벨은 「…」로 쓰고 기계로 검사** | 화면 이름이 바뀌면 검사가 바로 실패하므로 매뉴얼이 모르는 사이에 낡지 않는다. 견본의 check 방식과 같다 |
| D-8 | **렌더러는 marked 지연 로드 + DOMPurify** | 표·코드 블록·중첩 목록을 직접 파싱하면 버그가 생기기 쉽다. jsdelivr는 CSP에 이미 허용되어 있고 DOMPurify는 이미 로드되어 있다. 처음 열 때만 받으므로 첫 화면에는 영향이 없다 |
