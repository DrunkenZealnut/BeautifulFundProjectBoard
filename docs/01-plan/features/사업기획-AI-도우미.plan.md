## Executive Summary

| Perspective | Content |
|-------------|---------|
| **Problem** | 사업계획·기획안·제안서는 매번 백지에서 시작한다. 신청서·사업계획·변경신청서·기초연구보고서에 쌓인 문제의식, 단가, 성과지표, 재단 규정, 실제로 해보니 어땠는지가 사람 머릿속에만 있어서 새 문서를 쓸 때 다시 찾아 읽고, 옛 수치(변경 전)를 잘못 쓰거나 재단 규정(비목·표기)에 어긋난 계획을 내는 일이 생긴다. 2027년 2차년도 계획서와 하반기 결과보고서가 곧 필요하다 |
| **Solution** | 새 Claude Code 스킬 `/plan-lab` (`idea → plan → proposal → review`, `learn`, `status`). 지식베이스를 3층으로 확장한다 — ① 계획(현행 kb 01~08) ② **결과·실적**(`09-성과실적.md`: 산출물 대장·기초연구 결과·집행률·KPI 달성) ③ **교훈·결정**(`10-교훈.md`: 잘된 것/안 된 것/왜 바꿨나). 섹션 단위 색인(`kb-index.yaml`)으로 필요한 부분만 읽고, 모든 초안은 `facts.yaml` 인용 + `promo.py check`를 거친다 |
| **Function/UX Effect** | `/plan-lab idea 반도체고 졸업생 사후지원` 한 줄이면 kb의 빈틈(미달 KPI·미집행 예산·문제정의에서 안 다룬 대상)을 근거로 아이디어 8~10개가 자원·리스크·연결 사업과 함께 나오고, 고른 아이디어는 `/plan-lab plan`으로 재단 서식 골격(배경·목표·세부활동·일정·예산·성과지표·위험)의 계획서 초안이 된다. 공모 요강을 `data/`에 넣으면 `proposal`이 요구항목 ↔ 우리 근거를 매핑해 신청서 초안을 만든다. 결과물이 생길 때마다 `learn`으로 kb에 쌓여 다음 기획이 더 정확해진다 |
| **Core Value** | 1인 단체가 3년 인큐베이팅의 경험을 잃지 않고 축적한다. 계획서의 모든 숫자는 근거가 있고 재단 규정에 맞으며, 기획에 드는 시간이 며칠에서 반나절로 줄어 대표가 현장에 쓸 시간이 늘어난다 |

## 1. 현황 분석

### 1.1 이미 있는 것 (재사용)

| 자산 | 위치 | 기획에 쓰이는 방식 |
|------|------|-------------------|
| 단일 진실 원천 | `content/kb/facts.yaml` (org·program·units·budget·kpi·partners·deprecated·forbidden) | 계획서 수치·명칭 인용 원천, 예산 검산 |
| 서술 kb 8종 | `01-사업개요`(문제정의·설립목적·비전) `02-단위사업/*`(5개) `03-예산` `04-성과지표` `05-일정` `06-메시지` `07-변경이력` `08-재단규정` | 배경·목표·활동 설계의 맥락, 변경 이유, 규정 게이트 |
| 원천 문서 | `data/` 신청서·사업계획·예산·변경신청서·수행가이드 PDF, 기초보고서(`kb/_raw`) | kb가 답하지 못할 때 직접 인용 |
| 도구 | `content/tools/promo.py` (fill·render·check R1~R7·index·kb-extract·selftest), `md2hwpx.py` (proposal/report/gonmun/base) | 산출물 검사·HWPX 출력 그대로 사용 |
| 문서 골격 | `content/templates/docs/` 6종 (협력제안서·보고서·공문·보도자료·단체소개·안내문) | 기획 골격 3종을 같은 형식으로 추가 |
| 워크플로 관례 | `/promo brief→draft→…`, `content/out/<id>/` + `INDEX.md`, `status` 단계 | 동일 규약으로 `/plan-lab` 산출물 관리 |
| 산출물 실적 | `content/out/INDEX.md` 6건 final, 기초연구보고서 초안(2026-09-11) | "결과·실적" 층의 첫 입력 |

### 1.2 없는 것 (이 기능이 채울 것)

1. **결과·교훈 층**: kb는 전부 "계획" 문서에서 나왔다. 실제로 몇 개 학교에서 캠페인을 했는지, 기초연구에서 무엇을 발견했는지, 왜 8월에 계획을 바꿨는지(07은 "무엇을"만)는 정리돼 있지 않다 → 새 기획이 과거를 반복하거나 이미 확인된 문제를 놓친다
2. **발산 도구**: `/promo brief`는 목적이 정해진 요청만 받는다. "무엇을 할까"를 kb 근거로 넓히는 단계가 없다
3. **계획서 골격**: 재단 사업계획서·변경신청서 구조(배경→목표→세부활동→일정→예산→성과지표)와 예산 검산·비목 규칙을 강제하는 템플릿이 없다
4. **공모 대응**: 외부 공모 요강의 요구항목을 우리 근거에 매핑하는 절차가 없다
5. **컨텍스트 예산**: kb 340KB + data 864KB를 매번 다 읽을 수 없다. 섹션 색인이 없어서 스킬이 어떤 파일을 열지 SKILL.md에 하드코딩돼 있다

### 1.3 "학습"의 의미 (이 프로젝트에서)

파인튜닝·벡터DB가 아니다. Claude Code 세션 안에서 (a) **정제된 kb를 층별로 키우고** (b) **섹션 색인으로 필요한 근거만 불러와** (c) **facts만 인용하는 규칙**으로 답하는 것이 "학습"이다. 코퍼스가 작고(수백 KB) 단일 사용자이므로 이 방식이 가장 정확하고 비용이 없다. 코퍼스가 수십 MB로 커지면 그때 `kb-search`(로컬 BM25)를 붙인다 — §5 범위 제외 참조.

### 2.3 범위 제외 (YAGNI)

- 웹앱(index.html) 내 AI 페이지, 벡터DB·임베딩, 파인튜닝
- 앱 DB(게시판·집행내역) 자동 수집 — 사용자가 요약을 `learn`에 넘기는 방식으로 대체 (후속 후보)
- iCloud 문서 폴더 일괄 수집(회의록·인사 문서 포함, PII 위험) — 필요한 문서를 `data/`로 옮겨 `learn`
- 외부 자료 자동 검색(타 단체 사례·법령) — 사용자가 파일로 제공
- 재단 서식 HWPX 자동 채우기(변경신청서·결과보고서) — F-13 hwpx-fill 확장은 별도 기능
- 다국어, 협업 편집, 버전 비교 UI

## 3. 설계 결정

| # | 결정 | 근거 |
|---|------|------|
| D-1 | `/promo`에 서브커맨드를 붙이지 않고 **형제 스킬 `/plan-lab`** 을 만든다. kb·도구·출력 규약은 공유 | `/promo`는 "정해진 것을 알리기", `/plan-lab`은 "무엇을 할지 정하기". 어조 규칙·템플릿·체크 항목이 다르고, SKILL.md가 이미 120줄이라 합치면 라우팅이 흐려진다 |
| D-2 | 결과·교훈을 **kb 파일 2개(09·10) + facts.outcomes** 로 둔다 | 계획(01~08)과 섞이면 "변경 전/후"처럼 "계획/실적" 혼동이 생긴다. 파일 분리가 check 규칙(R2 방식)으로 강제하기 쉽다 |
| D-3 | 검색 대신 **섹션 색인** | 코퍼스가 작다. 색인은 결정적이고 검사 가능하며, Claude가 어떤 근거를 읽었는지 산출물에 남길 수 있다 |
| D-4 | `idea`는 **kb 빈틈 스캔**을 먼저 하고 발산한다 | 일반론 아이디어를 막는 장치. 모든 아이디어가 "우리 상황의 어떤 빈틈에서 나왔는지"를 갖게 된다 |
| D-5 | 예산은 **단가 × 수량**으로만 쓴다 (`03-예산` 단가 인용, 합계 검산은 check R4 확장) | 재단 예산서 형식이 그렇고, 총액만 있는 계획은 변경신청 때 다시 쪼개야 한다 |
| D-6 | `learn`은 **승인형**(kb-sync와 동일) | 회의록의 한 줄이 "교훈"으로 굳으면 이후 모든 기획에 영향을 준다. 자동 반영 금지 |
