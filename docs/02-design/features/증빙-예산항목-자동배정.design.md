## 1. 개요

### 1.1 설계 목표

1. 수취인·거래처 → 예산항목을 **규칙 → 이력 → 미배정** 순으로 결정하는 순수 함수 하나(`resolveBudgetAssignment`)를 두고, 모든 입력 경로(증빙 일괄등록·엑셀 일괄등록·단건 폼)가 이 함수를 쓴다
2. 일괄등록의 「입금확인증 PDF」 소스를 **「증빙 파일(PDF·사진)」** 로 넓혀 이체확인증·전자세금계산서·영수증을 종류 자동 판별로 받는다
3. 새 증빙이 기존 집행 건과 같은 거래면 **등록 대신 증빙 첨부**가 기본이 되게 해서 이중 등록을 막는다
4. F-14 동작(파서, 수수료 연동, 계좌번호 비저장, 증빙 헬퍼)은 바꾸지 않고 확장만 한다

### 1.2 데이터 흐름

```
 파일(PDF/JPG/PNG) ─┬─ PDF ─ extractPdfTextLines ─┬─ lines 있음 ─ detectEvidenceKind ─┬─ 'deposit' → parseDepositConfirmation (F-14)
                    │                              │                                   ├─ 'tax'     → parseTaxInvoice
                    │                              │                                   └─ 'unknown' → OCR (1페이지 렌더)
                    │                              └─ lines 없음(스캔본) ─ renderPdfPageToImage → OCR
                    └─ 이미지 ─ downscaleImage ───────────────────────────────────────────→ OCR (/api/receipt-ocr)
                                                                                              │
                                    EvidenceParsed { kind, execution_date, amount, recipient, bizNo, description, payment_method, fee?, warnings }
                                                                                              │
                          ┌───────────────────────────────────────────────────────────────────┤
                          ▼                                                                   ▼
        findMatchingExecution(기존 집행 + 증빙맵)                           resolveBudgetAssignment(규칙, 이력, 예산구조)
                          │                                                                   │
                          └──────────────► 미리보기 행 { _kind, _attachTo, _match, _assign*, _saveRule, ... } ◄──┘
                                                               │  (사용자 확인·수정: updateRow)
                                                               ▼
                         등록: 신규 행 insert + 증빙 업로드 / 첨부 행은 증빙 업로드만 → documents insert
                               → 규칙 upsert(_saveRule) + 규칙 적중 카운트 갱신
```

## 2. 데이터 모델

### 2.1 신규 테이블 `bf.payee_budget_rules`

파일: `supabase-migration-payee-rules.sql` (bf 스키마 직접, newsletters 마이그레이션과 같은 형식)

```sql
CREATE TABLE IF NOT EXISTS bf.payee_budget_rules (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id      uuid REFERENCES bf.projects(id) ON DELETE CASCADE,
    match_type      text NOT NULL CHECK (match_type IN ('biz_no', 'exact', 'contains')),
    pattern         text NOT NULL,          -- biz_no: 숫자 10자리 / exact·contains: normalizePayee() 결과
    display_name    text NOT NULL DEFAULT '',-- 화면 표시용 원래 표기 (예: "(주)한빛인쇄")
    subcategory_id  text NOT NULL,
    budget_item_id  text NOT NULL,
    payment_method  text CHECK (payment_method IN ('카드', '계좌이체')),  -- NULL = 증빙에서 온 값 유지
    notes           text DEFAULT '',
    is_active       boolean NOT NULL DEFAULT true,
    hit_count       integer NOT NULL DEFAULT 0,
    last_used_at    timestamptz,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT payee_rules_pattern_len CHECK (char_length(pattern) >= 2),
    CONSTRAINT payee_rules_uniq UNIQUE NULLS NOT DISTINCT (project_id, match_type, pattern)  -- PG15+
);
ALTER TABLE bf.payee_budget_rules ENABLE ROW LEVEL SECURITY;
-- select / insert / update / delete: USING (true) — 기존 테이블 공개 정책 패턴과 동일
CREATE INDEX IF NOT EXISTS idx_payee_rules_project ON bf.payee_budget_rules (project_id);
```

- **비목(`type`)은 저장하지 않는다**: 항목의 `type`은 예산구조(`budget_data`)에서 파생되므로 중복 저장하면 불일치가 생긴다
- **개인정보 없음**: 사업자번호(업체)와 이름만. 개인 수취인은 `exact`만 허용(UI에서 강제), 생년월일·계좌 등 저장 안 함
- `project_id = NULL` 규칙은 하드코딩 `BUDGET_DATA` 사용 시(프로젝트 미생성 환경)용

### 2.2 기존 테이블 변경

없음. `budget_executions.recipient`에는 지금처럼 원래 표기(공급자 상호/수취인성명)를 저장하고, 사업자번호는 `notes`에도 넣지 않는다(매칭 시점에만 사용).

## 3. 모듈 수준 순수 함수 (index.html, F-14 파서 블록 바로 아래)

모두 React 밖 순수 함수 — Babel 제약상 훅 사용 없음. Node에서 그대로 떼어 단위 테스트할 수 있게 전역 의존(`supabase`, state) 금지.

### 3.1 정규화

```javascript
// 거래처명 정규화: 법인 표기·공백·괄호·특수문자 제거, 소문자화 — 규칙 저장·조회·이력 집계·매칭 공용
const PAYEE_CORP_RE = /\(주\)|㈜|주식회사|\(유\)|유한회사|\(재\)|재단법인|\(사\)|사단법인|\(합\)|합자회사/g;
const normalizePayee = (s) => String(s || '')
    .replace(PAYEE_CORP_RE, '')
    .replace(/[\s()\[\]{}·.,\-_'"]/g, '')
    .toLowerCase();

// 사업자번호: 숫자 10자리만 유효
const normalizeBizNo = (s) => { const d = String(s || '').replace(/\D/g, ''); return d.length === 10 ? d : ''; };
```

### 3.2 예산구조 조회

```javascript
// budgetData(= effectiveBudgetData)에서 소분류·항목·대분류를 한 번에 찾음. 없으면 null
const findBudgetItem = (budgetData, subId, itemId) => {
    for (const cat of budgetData?.categories || []) {
        const sub = cat.subcategories.find(s => s.id === subId);
        if (!sub) continue;
        const item = sub.items.find(it => it.id === itemId);
        return item ? { cat, sub, item } : null;
    }
    return null;
};
```

일괄등록 insert(`allSubcats.find` + `categories.find` 3단 조회)와 단건 폼도 이 함수로 교체해 조회 로직을 하나로 모은다.

### 3.3 배정 해석기

```javascript
// 규칙 → 이력 → 미배정. 반환값의 subcategory_id/budget_item_id가 ''면 미배정
// rules: 현재 프로젝트의 활성 규칙 / executions: data.budgetExecutions (이미 프로젝트 필터됨)
const resolveBudgetAssignment = ({ payee, bizNo }, { rules, executions, budgetData }) => {
    const none = { subcategory_id: '', budget_item_id: '', source: null, ruleId: null, candidates: [] };
    const key = normalizePayee(payee);
    const biz = normalizeBizNo(bizNo);
    const valid = r => !!findBudgetItem(budgetData, r.subcategory_id, r.budget_item_id);

    // 1) 규칙: biz_no → exact → contains(긴 pattern 우선). 예산에서 사라진 항목을 가리키는 규칙은 건너뜀
    const active = (rules || []).filter(r => r.is_active && valid(r));
    const rule =
        (biz && active.find(r => r.match_type === 'biz_no' && r.pattern === biz)) ||
        (key && active.find(r => r.match_type === 'exact' && r.pattern === key)) ||
        (key && active.filter(r => r.match_type === 'contains' && key.includes(r.pattern))
                      .sort((a, b) => b.pattern.length - a.pattern.length)[0]);
    if (rule) return { ...none, subcategory_id: rule.subcategory_id, budget_item_id: rule.budget_item_id,
                       payment_method: rule.payment_method || null, source: 'rule', ruleId: rule.id };

    // 2) 이력: 같은 정규화 수취인의 (소분류,항목) 빈도 → 동률이면 최근 집행일
    if (!key) return none;
    const tally = new Map();
    (executions || []).forEach(e => {
        if (normalizePayee(e.recipient) !== key || !e.subcategory_id || !e.budget_item_id) return;
        if (!findBudgetItem(budgetData, e.subcategory_id, e.budget_item_id)) return;
        const k = `${e.subcategory_id}|${e.budget_item_id}`;
        const t = tally.get(k) || { subcategory_id: e.subcategory_id, budget_item_id: e.budget_item_id, count: 0, lastDate: '' };
        t.count += 1;
        if ((e.execution_date || '') > t.lastDate) t.lastDate = e.execution_date || '';
        tally.set(k, t);
    });
    const candidates = [...tally.values()]
        .sort((a, b) => b.count - a.count || b.lastDate.localeCompare(a.lastDate)).slice(0, 3);
    if (candidates.length === 0) return none;
    // 최빈 항목이 2회 이상이고 유일할 때만 자동 배정 (1회 이력·동명이인·다항목 거래처는 후보만 제시)
    const [top, second] = candidates;
    if (top.count < 2 || (second && second.count === top.count)) return { ...none, candidates };
    return { ...none, subcategory_id: top.subcategory_id, budget_item_id: top.budget_item_id, source: 'history', candidates };
};
```

- 이체수수료 행(`_kind: 'fee'`)에는 해석기를 적용하지 않는다(F-14 본 행 연동 유지)
- 규칙 전달 순서: 현재 프로젝트 규칙을 `project_id NULL`(공통) 규칙보다 앞에 정렬 → 같은 패턴이면 프로젝트 규칙 우선. 규칙 탭 수정 시 원래 `project_id` 유지
- 엑셀 행 중 입금(열 매핑된 구분 값이 출금/지급/이체가 아님)은 자동배정하지 않는다 — 환불 등이 지출로 등록되는 것 방지
- PDF(입금확인증) 행은 규칙의 `payment_method`와 무관하게 `계좌이체` 고정
- 수취인 `신한은행`은 이력 집계 대상에서 제외하지 않는다 — 해석기는 fee 행에 쓰이지 않으므로 영향 없음. 단 규칙 제안(§5.4)에서는 제외

### 3.4 증빙 종류 판별

```javascript
const TAX_INVOICE_TITLE_RE = /전\s*자\s*(세\s*금\s*)?계\s*산\s*서/;
const DEPOSIT_TITLE_RE = /입\s*금\s*확\s*인\s*증|이\s*체\s*확\s*인\s*증/;
// lines: extractPdfTextLines 결과. 제목 줄은 상단 5줄 안에 있다고 가정, 없으면 라벨 수로 판정
const detectEvidenceKind = (lines) => {
    if (!lines || lines.length === 0) return 'scan';
    const head = lines.slice(0, 5).join(' ');
    if (TAX_INVOICE_TITLE_RE.test(head)) return 'tax';
    if (DEPOSIT_TITLE_RE.test(head)) return 'deposit';
    const all = lines.join(' ');
    if (/공\s*급\s*가\s*액/.test(all) && /세\s*액/.test(all)) return 'tax';
    if ((all.match(DEPOSIT_LABEL_RE) || []).length >= 3) return 'deposit';
    return 'unknown'; // → OCR
};
```

### 3.5 전자세금계산서 파서

홈택스 발급 전자(세금)계산서 PDF(1페이지)를 대상으로 한다. 공급자/공급받는자 블록이 좌/우 2열이라 같은 라벨(`등록번호`, `상호`)이 한 줄에 2번 나온다 → x 정렬된 줄에서 **첫 등장 = 공급자**.

**라벨 표 (v0.1 잠정 — 샘플 2~3건으로 Do 착수 전 확정)**

| key | 라벨 | 용도 | 비고 |
|-----|------|------|------|
| `bizNo` | 등록번호 | 공급자 사업자번호 | 한 줄 2회 → 배열로 수집 |
| `corp` | 상호(법인명), 상호 | `recipient` | 한 줄 2회 → 배열 |
| `ceo` | 성명, 대표자 | 소비만 (저장 안 함) | 공급받는자 대표 이름 소비용 |
| `addr` | 사업장주소, 사업장 | 소비만 | |
| `bizType` | 업태 / `bizItem` 종목 | 소비만 | |
| `email` | 이메일 | 소비만 | |
| `date` | 작성일자, 작성일 | `execution_date` | |
| `supply` | 공급가액 | 메모 | 품목 표 헤더와 구분: 첫 숫자값만 |
| `tax` | 세액 | 메모 | |
| `total` | 합계금액 | `amount` | 값이 다음 줄에 있을 수 있음 |
| `approval` | 승인번호 | 소비만 | |

```javascript
const TAX_INVOICE_LABELS = [ /* 위 표, 긴 라벨 우선 — DEPOSIT_PDF_LABELS와 같은 { key, labels } 형식 */ ];
const TAX_LABEL_RE = new RegExp(TAX_INVOICE_LABELS.map(l => `(${l.labels.map(_spaced).join('|')})`).join('|'), 'g');

// parseDepositConfirmation의 줄 스캔 루프를 공용 함수로 추출 (F-14 동작 불변)
// 반환: { [key]: string[] } — 같은 key의 모든 등장값을 순서대로 (입금확인증은 [0]만 사용)
const scanLabelValues = (lines, table, re, skipRe) => { /* F-14 루프와 동일, raw[key]를 배열로 push */ };

// orgBizNo: 우리 단체 고유번호(orgSettings.org_registration_number) — 공급자/공급받는자 뒤바뀜 방어
const parseTaxInvoice = (lines, fileName = '', orgBizNo = '') => {
    const raw = scanLabelValues(lines, TAX_INVOICE_LABELS, TAX_LABEL_RE, /이 금액을|청구|영수/);
    const bizNos = (raw.bizNo || []).map(normalizeBizNo).filter(Boolean);
    const corps = raw.corp || [];
    let si = 0; // 공급자 인덱스
    const org = normalizeBizNo(orgBizNo);
    if (org && bizNos[0] === org && bizNos[1]) si = 1; // 첫 등장이 우리 단체면 반대쪽이 공급자
    const firstNum = arr => { for (const v of arr || []) { const d = parseInput(v || ''); if (d) return Number(d); } return null; };
    const total = firstNum(raw.total) ?? nextLineNumberAfter(lines, /합\s*계\s*금\s*액/); // 다음 줄 폴백
    const supply = firstNum(raw.supply), tax = firstNum(raw.tax);
    const isTaxFree = !/세\s*금/.test(lines.slice(0, 5).join(' ')); // "전자계산서" = 면세
    const itemName = extractFirstItemName(lines); // "MM DD 품목 ..." 행의 품목, 없으면 ''
    const warnings = [];
    if (!raw.date?.[0]) warnings.push('작성일자 미인식');
    if (total == null) warnings.push('합계금액 미인식');
    if (supply != null && tax != null && total != null && supply + tax !== total) warnings.push('공급가액+세액≠합계');
    return {
        kind: 'tax', isTaxFree,
        execution_date: normalizeDate(raw.date?.[0]),
        amount: total,
        recipient: (corps[si] || '').trim(),
        bizNo: bizNos[si] || '',
        description: itemName || fileName.replace(/\.pdf$/i, '').trim(),
        payment_method: '계좌이체',
        memo: supply != null ? `공급가액 ${fmt(supply)} / 세액 ${fmt(tax || 0)}` : '',
        warnings
    };
};
```

- 수정세금계산서(합계 음수)·2페이지 이상은 `warnings`에 `'수정/다장 세금계산서 — 직접 확인'` 추가, 기본 선택 해제
- 공급받는자 대표 성명·주소·이메일은 라벨로 소비만 하고 결과 객체에 넣지 않는다 (F-14 계좌번호와 같은 원칙)

### 3.6 기존 집행 매칭

```javascript
// kind별 날짜 허용 오차(일): 입금확인증은 같은 날, 세금계산서는 발행일≠지급일이 흔함
const MATCH_DATE_WINDOW = { pdf: 0, tax: 10, receipt: 3 };
const dayDiff = (a, b) => Math.abs((new Date(a) - new Date(b)) / 86400000);
const payeeMatches = (a, b) => {
    const x = normalizePayee(a), y = normalizePayee(b);
    return !!x && !!y && (x === y || (Math.min(x.length, y.length) >= 2 && (x.includes(y) || y.includes(x))));
};
// docsMap: executionDocsMap, docName: 이 증빙이 들어갈 슬롯 → hasDoc 판정
const findMatchingExecution = (executions, cand, { kind, docsMap, docNameFor }) => {
    if (!cand.execution_date || !(cand.amount > 0)) return null;
    const win = MATCH_DATE_WINDOW[kind] ?? 0;
    const hits = (executions || []).filter(e =>
        Number(e.amount) === cand.amount &&                    // 금액은 완전 일치만 (OCR 오인식 건 오매칭 방지)
        dayDiff(e.execution_date, cand.execution_date) <= win &&
        payeeMatches(e.recipient, cand.recipient));
    if (hits.length === 0) return null;
    hits.sort((a, b) => dayDiff(a.execution_date, cand.execution_date) - dayDiff(b.execution_date, cand.execution_date));
    const e = hits[0];
    const docName = docNameFor(e.type);
    return { id: e.id, execution_date: e.execution_date, amount: Number(e.amount), recipient: e.recipient,
             budget_item_name: e.budget_item_name, type: e.type, docName, hasDoc: !!docsMap?.[e.id]?.[docName], multiple: hits.length > 1 };
};
```

F-14 중복 판정은 두 경로로 나뉜다 — **업로드 내 중복**: `executionDupKey + 적요` 키를 `seen` Set으로 검사 / **기존 집행 중복**: `matchDuplicateExecutions`(1:1 매칭, `withPdfDups`가 호출). 2차 매칭은 이 결과와 함께 쓴다.

### 4.2 Claude 호출

- 모델 `claude-sonnet-5`, `max_tokens: 800`, urllib timeout 25s (`vercel.json` maxDuration 30)
- **도구 강제 호출로 JSON 고정**: `tools: [{ name: 'record_evidence', input_schema: <위 result 스키마> }]`, `tool_choice: { type: 'tool', name: 'record_evidence' }` → 응답의 `tool_use.input`만 반환
- 시스템 프롬프트 요지:
  - 한국 영수증·카드전표·세금계산서·이체확인증 이미지에서 지정 필드만 추출
  - 금액은 최종 결제(합계) 금액, 부가세 포함
  - **카드번호·승인번호·계좌번호·개인 연락처·주민번호는 절대 출력하지 않는다** (스키마에도 없음)
  - 읽을 수 없으면 null, 추측 금지, 불확실하면 `confidence: low`
- 서버 검증: `media_type` ∈ {jpeg,png,webp}, base64 길이 상한, JSON 파싱 실패 → 400. `biz_no`는 서버에서 숫자 10자리 아니면 null로 정리, `total`은 int 변환
- 로깅: 예외 타입만 기록. 이미지·추출 결과는 로그/저장 금지
- CORS: 같은 출처 호출이므로 `Access-Control-Allow-Origin: *` 헤더를 **넣지 않는다**. `Origin`이 있고 허용 목록(배포 도메인·`*.vercel.app` 프리뷰·`localhost`)이 아니면 403 — 공개 엔드포인트로 API 키가 남용되는 것을 줄이는 최소 방어

### 5.6 미리보기 표 UI 변경

- **액션 바**: `🔗 규칙·이력으로 빈 항목 채우기` 버튼 — `_assignLocked`가 아니고 항목이 빈 행(엑셀 행 포함)에 해석기 일괄 적용. 엑셀 행은 `rowName(r)`(열 매핑에서 파생)을 payee로 사용 → 열 매핑 바꾼 뒤 다시 누르면 된다
- **소분류·항목 셀 아래 배지**: `📌 규칙`(파랑) / `🕘 이력 n회`(회색) / `❓ 미배정`(주황). 후보 2개 이상이면 `후보 ▾` 작은 select
- **「규칙 저장」 체크박스 열**: 신규 모드 + 수취인 있음 + fee 아님일 때만 표시. 체크 기본값은 5.5 규칙
- **모드 셀** (증빙 행만): `🆕 신규 등록` ↔ `📎 기존 건에 첨부` 토글. 첨부 모드면 `YYYY-MM-DD · 항목명 · 금액` 요약을 소분류·항목 자리에 표시
- **종류 배지**: `이체확인증` / `세금계산서` / `계산서(면세)` / `영수증(AI)` / `카드전표(AI)`

`notes`(세금계산서 공급가액/세액 메모)는 insert 행의 `notes`에 넣는다.

### 5.8 단건 등록 폼

- 「📎 입금확인증 PDF로 자동입력」 → **「📎 증빙으로 자동입력 (PDF·사진)」**. 같은 파이프라인(`parseEvidenceFile(file, worker?)` 공용 함수로 §5.4 분기 추출)
- 자동입력 후:
  1. `formData` 필드 채움 (현행 + `notes` 메모)
  2. `formData.subcategory_id`가 비어 있으면 해석기 결과로 소분류·항목·`type`·이름 필드까지 채우고 `setFormAssign`
  3. `findMatchingExecution` 결과가 있고 `!hasDoc`면 폼 상단 배너: `이 증빙은 이미 등록된 [날짜 · 항목 · 금액] 건과 같은 거래로 보입니다.` [기존 건에 증빙만 첨부] [새로 등록] — 첨부 버튼은 `uploadExecutionDoc` + `insertExecutionDocs` 후 폼 리셋
- 예산 분류 라벨 옆에 배정 배지, 예산 항목 아래 `☐ 이 거래처(수취인)를 규칙으로 저장` 체크박스 (`formSaveRule`, 미배정에서 직접 고르면 자동 체크)
- 제출 성공 후 `persistRuleEffects([{ payee: formData.recipient, bizNo: formEvidence?.parsed.bizNo, … }])`
- 자동 첨부 슬롯은 `pickEvidenceDocName(getRequiredDocuments(type, pm), formEvidence.kind, …)`

### 5.9 「🔗 거래처 규칙」 서브탭 (`budgetTab === 'rules'`)

탭 버튼은 `import`(일괄등록) 오른쪽에 추가.

```
[안내] 이체대상·거래처를 예산항목에 연결해두면 증빙 등록 시 자동으로 배정됩니다.
[payeeRulesError 있으면] ⚠ 규칙 테이블이 없습니다. supabase-migration-payee-rules.sql을 실행하세요.

── 규칙 목록 (N) ───────────────────────────── [+ 규칙 추가]
 표시명 | 매칭(+패턴) | 소분류 > 항목 | 결제 | 사용 | 최근 사용 | (꺼진 규칙은 흐리게) | [수정][끄기/켜기][삭제]
 · 항목이 예산에 없으면 행 빨간 배경 + "⚠ 항목 없음"
 · 정렬: 사용횟수 desc

── 이력에서 규칙 만들기 ─────────────── [선택 n건 규칙으로 저장]
 ☐ 수취인 | 집행 n건 | 소분류 > 항목 (비율)
```

- **추가/수정 폼**(`ruleEdit`): 표시명 입력 시 `pattern` 자동 = `normalizePayee(표시명)`. 매칭 방식 `exact`(기본)/`contains`/`biz_no`. `biz_no` 선택 시 패턴 입력란이 사업자번호(하이픈 허용 → `normalizeBizNo`)로 바뀜. `contains`는 패턴 2자 이상 경고 + "개인 이름에는 쓰지 마세요" 도움말
- **삭제**는 `confirm` 후 delete, **끄기**는 `is_active` 토글
- **이력 제안 `computeRuleSuggestions(executions, rules, budgetData)`** (모듈 수준 순수 함수):
  - `normalizePayee(recipient)`로 묶고 `신한은행`·빈 이름·`description`이 `이체수수료`로 시작하는 건 제외
  - 건수 ≥ 2, 최빈 (소분류,항목) 비율 ≥ 80%, 예산에 존재, 이미 exact/contains 규칙이 적용되는 수취인 제외
  - 결과 `{ key, display_name(가장 최근 원표기), count, subcategory_id, budget_item_id, ratio }`
